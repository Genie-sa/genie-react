---
title: "Select one row and all 100 redraw: the inline arrow that breaks PureComponent"
description: Genie counted 100 IssueRow renders for one checkbox click, named the new onToggle arrow as the cause, and verified the fix at one render.
---

Ticking one checkbox in a 100-row issue table re-rendered all 100 `IssueRow` components. `IssueTable` passes each row a new `onToggle` arrow on every render, so the row's `PureComponent` shallow prop check always fails. After the fix, the same click rendered one row, and `genie-react verify` went from `fail` (exit 1) to `pass` (exit 0).

Every command below ran on 2026-11-19 with Genie 1.1.0 against `apps/realworld-legacy` in this repository, a React 18.3 app with webpack, Redux and `connect()` class components. The full log is in the [evidence file](https://github.com/Genie-sa/genie-react/blob/main/docs/article-evidence/one-click-redraws-100-rows.md). Output blocks are trimmed to the fields shown, and long source paths are cut to `…/src/`.

## The symptom

The answer key for this seeded bug reports it the way a user would.

> Ticking one checkbox in the issue table lags. It looks like every row on the page redraws.

The `/issues` page shows 100 rows. The browser driver is [agent-browser](https://github.com/vercel-labs/agent-browser), with the session name `upd-c`.

The row wrote nothing to the DOM. Its only updates were two event handlers. The source location points at line 48 of `issue-table.tsx`, where the rows are created:

```tsx
{rows.map((issue) => (
  <IssueRow
    key={issue.id}
    issue={issue}
    selected={selectedIds.includes(issue.id)}
    onToggle={() => this.props.selectionToggled(issue.id)}
    onOpen={this.openIssue}
  />
))}
```

## Why PureComponent does not help

`IssueRow` extends `PureComponent`, which skips a render when every prop is `===` to its previous value. `onOpen` passes that check, because `openIssue` is a class field created once. `onToggle` never does. Selecting a row dispatches `selectionToggled`, the store's `selectedIds` changes, `connect()` re-renders `IssueTable`, and `render()` creates 100 new arrows. Every row sees a new function and renders.

A function row wrapped in `React.memo` has the same problem, because `memo` also compares each prop with `Object.is`. Either way, the parent must stop creating a new function per row.

## The fix

Pass the bound action creator, which `connect()` keeps stable, and let the row supply its own id:

```diff
--- a/apps/realworld-legacy/src/features/issues/issue-table.tsx
+++ b/apps/realworld-legacy/src/features/issues/issue-table.tsx
-                onToggle={() => this.props.selectionToggled(issue.id)}
+                onToggle={this.props.selectionToggled}
--- a/apps/realworld-legacy/src/features/issues/issue-row.tsx
+++ b/apps/realworld-legacy/src/features/issues/issue-row.tsx
-  onToggle: () => void
+  onToggle: (id: string) => void
-            onChange={onToggle}
+            onChange={() => onToggle(issue.id)}
```

The row still creates an arrow for `onChange`, but inside its own render. That arrow reaches only the `<input>`, so it costs nothing when the row itself skips rendering.

## The proof

The claims say what the fix must make true. At most one `IssueRow` renders, `IssueTable` renders at least once so a click that misses the app fails, and no error boundary catches. The `min 1` claim matters. Zero row renders satisfies `max 1`, so without a positive control a click that never reached the table could not fail. ## Where this approach stops

- Genie counted renders, not milliseconds. This run did not measure how long the click took. For timing, take repeated captures and compare them as the [optimize guide](/docs/guides/optimize) describes, and remember that development timings do not predict production.
- The first read on a large list can run out of analysis budget. Genie says so with `mountedUnknown` and `budgetAdvice` instead of returning a short count. Follow the advice, repeat the action, and read again.
- `verify` decides claims about React. It does not check what the user sees, so confirm the screen with your driver, as above.
- In the same app, other store actions also re-render `IssueTable`, because its selector returns a new page object. That is a separate seeded bug. This fix stops the 100 row renders, but `IssueTable` itself still renders on unrelated actions.

[Verify a fix](/docs/guides/verify-a-fix) lists every claim form. [Renders and effects](/docs/guides/renders-and-effects) covers render causes in more depth.
