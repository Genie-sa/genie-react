---
title: "Why did this React component re-render? Get the exact prop, hook, or context"
description: One sidebar click re-rendered 41 components in a React 19 dashboard. Genie named the hook, prop, context and parent behind each render, and verify proved the fix.
---

Open a Genie window, do the interaction once, and run `react_render_causes`. It lists every render
with the input that caused it, such as a changed prop, a state hook, a context value or a parent
render, and grades each cause `exact`, `inferred` or `unknown`.

This page follows one real bug in `apps/realworld-dashboard`, a Vite and React 19 app in this repo
with seeded bugs. Your agent drives the page with agent-browser and asks Genie what React did. Every
output below comes from one run on November 19, 2026, trimmed to selected fields. The full log is in
the [evidence file](https://github.com/Genie-sa/genie-react/blob/main/docs/article-evidence/why-did-this-react-component-re-render.md).

## Collapsing the sidebar re-renders the stat cards

On the dashboard, click **Collapse sidebar**. Only the sidebar changes on screen. Genie sees more.
The output is trimmed to 9 of its 40 rows:

```bash
npx genie-react call react_clear_renders '{}' --session art-m5
agent-browser --session art-m5 find role button click --name 'Collapse sidebar'
npx genie-react call react_quiesce '{"idleMs":500,"timeoutMs":10000}' --fail-on-result-error --session art-m5
npx genie-react call react_get_renders '{"limit":40}' --session art-m5 --fields name,renders,necessity,necessityReason
```

```text
[40]:
  each: {renders:1}
  - {name:AppShell,necessity:necessary,necessityReason:dom-changed}
  - {name:PreferencesProvider,necessity:necessary,necessityReason:dom-changed}
  - {name:SidebarNav,necessity:necessary,necessityReason:dom-changed}
  - {name:TopBar,necessity:unnecessary,necessityReason:inputs-unchanged}
  - {name:UserMenu,necessity:unknown,necessityReason:callbacks-changed}
  - {name:StatCard,necessity:unnecessary,necessityReason:output-unchanged}
  - {name:StatCard,necessity:unnecessary,necessityReason:output-unchanged}
  - {name:StatCard,necessity:unnecessary,necessityReason:output-unchanged}
  - {name:StatCard,necessity:unnecessary,necessityReason:output-unchanged}
```

The same read with `"limit":200` returned 41 rows. One click rendered 41 components. The four
`StatCard` components are wrapped in `memo` and show revenue and order numbers that did not change.

## One read names four kinds of cause

```bash
npx genie-react call react_render_causes '{"limit":100}' --session art-m5
```

Trimmed to five of the 41 events:

```text
  AppShell #14696656666673 {…,necessity:necessary,necessityReason:dom-changed,…,source:{location:/src/routes/_app.tsx:21:9,ownership:app}}
    ← state exact "state[0]"
  PreferencesProvider #14696656666674 {…,source:{location:/src/layout/app-shell.tsx:36:5,ownership:app}}
    ← parent inferred AppShell
    ← children exact
  SidebarNav #14696656666677 {…,source:{location:/src/layout/app-shell.tsx:38:9,ownership:app}}
    ← parent inferred PreferencesProvider {origin:AppShell}
    ← props exact collapsed
  TopBar #14696656666679 {…,necessity:unnecessary,necessityReason:inputs-unchanged,…}
    ← parent inferred PreferencesProvider {origin:AppShell}
  StatCard #14696656666854 {…,necessity:unnecessary,necessityReason:output-unchanged,…,source:{location:/src/features/dashboard/dashboard-page.tsx:55:9,ownership:app}}
    ← context exact "Context(PreferencesProvider)" {contextIndex:0}
```

Each `←` line is one cause: its kind, its grade and its name. `AppShell` rendered because its first
`useState` changed. That hook holds `collapsed`. `SidebarNav` rendered because its `collapsed` prop
changed. `TopBar` had no input change and rendered because its parent did. Its `origin` names
`AppShell` as the component whose own update started the cascade.

The `StatCard` line is the bug. It rendered because the value of the context that
`PreferencesProvider` provides changed. Nine renders in this click carry that cause: the four
`StatCard`s, `UserMenu`, `NotificationsDrawer` and three dashboard cards.

## A context value rebuilt on every render

The full view shows what changed inside the context value:

```bash
npx genie-react call react_render_causes '{"component":"StatCard","limit":1,"view":"full"}' --session art-m5
```

```text
    ← context exact "Context(PreferencesProvider)" {contextIndex:0,contextId:context:1,provider:{componentId:14696656666674,componentName:PreferencesProvider},…,deepDiff:{changes:[{kind:identity-changed-uninspected,path:/setTheme},{kind:identity-changed-uninspected,path:/setLocale}],visited:13,truncated:true}}
```

Theme, locale and the formatters kept their values. Only `setTheme` and `setLocale` are new
functions. `PreferencesProvider` sits inside `AppShell`, so the sidebar state change re-renders it,
and it builds both functions and the value object again:

```tsx title="apps/realworld-dashboard/src/app/preferences.tsx"
const setTheme = (next: Theme) => {
  window.localStorage.setItem(THEME_KEY, next)
  setThemeState(next)
}
// setLocale is built the same way.

const value: PreferencesContextValue = {
  ...formatters,
  theme,
  resolvedTheme,
  locale,
  setTheme,
  setLocale,
}
```

A new value object makes every `usePreferences()` consumer render. [A memoized component still
re-renders when a context it uses changes](https://react.dev/reference/react/memo).

## The fix keeps the value stable

This is the reference fix from the app's answer key. It was applied for the "after" run and then
reverted, so the bug stays in the repo for other runs:

```diff
-  const setTheme = (next: Theme) => {
+  const setTheme = useCallback((next: Theme) => {
     window.localStorage.setItem(THEME_KEY, next)
     setThemeState(next)
-  }
-  const setLocale = (next: Locale) => {
+  }, [])
+  const setLocale = useCallback((next: Locale) => {
     window.localStorage.setItem(LOCALE_KEY, next)
     setLocaleState(next)
-  }
+  }, [])

-  const value: PreferencesContextValue = {
-    ...formatters,
-    theme,
-    resolvedTheme,
-    locale,
-    setTheme,
-    setLocale,
-  }
+  const value = useMemo<PreferencesContextValue>(
+    () => ({ ...formatters, theme, resolvedTheme, locale, setTheme, setLocale }),
+    [formatters, theme, resolvedTheme, locale, setTheme, setLocale],
+  )
```

The import line also gains `useCallback`.

## Verify proves the fix

`verify` turns the finding into claims with an exit code. `StatCard` must not render, and
`SidebarNav` must render at least once, so a click that missed the app fails:

```bash
npx genie-react verify begin --session art-m5 --name 'collapse the sidebar' \
  --claim 'render StatCard max 0' --claim 'render SidebarNav min 1'
agent-browser --session art-m5 find role button click --name 'Collapse sidebar'
npx genie-react verify end vfy_71b10ec6-0771-4d52-b276-c2dba5320078 --session art-m5
```

Before the fix, trimmed to the verdict and claim lines. The command exited with code 1:

```text

  1 fail render StatCard max 0  {renders:4,mounts:0,updates:4,remounts:0,semantics:exact,instances:4,activeInstances:4}
  2 pass render SidebarNav min 1  {renders:1,mounts:0,updates:1,remounts:0,semantics:exact,instances:1,activeInstances:1}
```

After the fix, the same claims and the same click. The command exited with code 0:

```text
pass vfy_c211e1b5-26e0-409a-a2e9-e69597aad74f "collapse the sidebar"  1 commit, quiet after 723 ms (react, query, router)
  1 pass render StatCard max 0  {renders:0,mounts:0,updates:0,remounts:0,semantics:exact,instances:4,activeInstances:4}
```

A fresh `react_get_renders` capture of the same click after the fix listed 16 renders instead of
41, and its coverage reported `complete: true`.

The first "before" run also had `--claim 'boundaries clean'`. It failed on a different seeded bug.
The carrier card's error boundary held `Cannot read properties of null (reading 'toFixed')`. That
claim would fail after this fix too, so the runs above leave it out to compare like with like.

## What exact, inferred and unknown mean in practice

`exact` means Genie saw the link directly. In the run above, it saw the state slot change, the
`collapsed` prop change and the context value change, and it named the provider. Act on an `exact`
cause.

`inferred` means the link is likely but not proven. The `parent` causes above are inferred. Here is
a second kind. On the Orders page, ticking one order's checkbox also rendered `SidebarNav`:

```text
  SidebarNav #3080045199402 {…,necessity:unnecessary,necessityReason:output-unchanged,inputEvidence:none-observed,…}
    ← external-store inferred anonymous-external-store
```

The full view adds `subscriptionFired:true`, `selector:null` and `changedFields:[selectedOrderIds]`.
`SidebarNav` does not show the selection, so confirm the lead in the code.
`src/layout/sidebar-nav.tsx` calls `useWorkspaceStore()` without a selector, so it subscribes to the
whole zustand store. That is another seeded bug in the same app.

`unknown` means Genie saw a render but cannot name its cause. Typing one character into
**Filter orders** rendered `OrdersPage` twice:

```text
  OrdersPage #12145244766261 {renderEventId:render:18:55,…,necessity:necessary,necessityReason:dom-changed,…}
    ← unknown unknown {reason:unclassified-hook-changed}
  OrdersPage #12145244766261 {renderEventId:render:17:23,…,necessity:necessary,necessityReason:dom-changed,…}
    ← state exact "state[0]"
```

The earlier render, `render:17:23`, came from the `term` state. The full view of the
second gives `hookIndex:10`, and `react_inspect_component` lists that hook as
`{index:10,kind:other,hook:useDeferredValue,stateful:false,value:x}`. It is React's deferred render
for `useDeferredValue(term)`. Coverage for this capture was `complete: true`, so the `unknown`
reflects a hook kind Genie does not classify, not missing data. Genie says so instead of guessing.

## When this approach does not fit

Read `coverage` before you trust a missing cause. The sidebar capture reported `complete: false`
with `inputs-truncated` on 9 fibers, because Genie compares functions by identity and does not look
inside them. Causes it did report were still graded, but an absent cause proves nothing until
coverage is complete. [Read evidence](/docs/reference/evidence) lists every gap and its fix.

`necessity` is not permission to delete a render. The full `StatCard` event says
`optimizationSafety: not-proven-safe`, so check the screen with your driver after any change.

Render causes explain why React rendered, not how long it took. For time, use the timeline and
repeated captures in [Optimize a slow interaction](/docs/guides/optimize). Genie needs a React 18 or
newer development build. To lock in a fix, see [Verify a fix](/docs/guides/verify-a-fix).
