title: We planted 15 bugs in a legacy React and Redux app. Here's what an agent could prove

---

Genie's evidence proved the defect for 11 of the 15 bugs seeded in our legacy React and Redux app, and showed only the symptom for the other 4. `genie-react verify` went from `fail` to `pass` for 10 of the reference fixes. The other 5 bugs live in requests, a Suspense boundary, a class timer or misplaced component state, which no `verify` claim can express, so a repeated tool read proved those fixes instead.

## The app and the run

`apps/realworld-legacy` is a project tracker written the way a 2019 codebase looks today. It runs React 18.3 in `StrictMode`, webpack 5 with Babel, Redux Toolkit 1.9 beside hand-written reducers and thunks, `connect()` class components, reselect and RTK Query. Its answer key in `evals/realworld/legacy` lists 15 bugs, each with a user's symptom, the cause, a reference fix, and a grade for what Genie can show. The grade is `full` when Genie's tools prove the defect and `partial` when they show the symptom but not the cause.

Every command ran on 2026-11-19 against commit `6867352`. The dev server ran on port 5211 with its own hub on 15212:

```bash
GENIE_HUB_PORT=15212 npx genie-react hub --port 15212
PORT=5211 GENIE_HUB_PORT=15212 pnpm exec webpack serve --mode development --port 5211
agent-browser --session art-l1 open http://127.0.0.1:5211/
npx genie-react status --session art-l1 --wait 15000
```

```text
ready: true
app: {name:"Acme Tracker",url:http://127.0.0.1:5211/login,reactVersion:18.3.1,reactMounted:true}
domains: [session,react,memory,perf,timeline,redux,app]
```

For each bug we drove the symptom with [agent-browser](https://github.com/vercel-labs/agent-browser), read Genie's evidence, ran `verify` where a claim fit, applied the answer key's fix, ran it again, and reverted with git. Output below is trimmed to the fields shown, and the full log is in the [evidence file](https://github.com/Genie-sa/genie-react/blob/main/docs/article-evidence/we-planted-13-bugs-in-a-legacy-react-app.md).

## What full evidence looks like

Full evidence points at a line of code or a specific value. For the lost title draft, `react_render_causes` with `"appOnly":false,"view":"full"` showed the second render and the `setState` that caused it (jq summary of the JSON output):

```text
{"commit":33,"causes":[{"kind":"state","evidence":"exact","name":"this.state.draft","classUpdates":[{"fields":["draft"],"phase":"lifecycle","evidence":"exact","caller":{"functionName":"IssueTitleEditor.componentDidUpdate","file":"issue-title-editor.tsx","line":22}}]}]}
{"commit":32,"causes":[{"kind":"parent","evidence":"inferred","name":null,"classUpdates":null},{"kind":"props","evidence":"exact","name":"issue","classUpdates":null}]}
```

Commit 32 delivered a refetched `issue` object. Commit 33 overwrote the draft from `componentDidUpdate`. Line 22 is the reset.

For the missing note, Genie's Redux collector caught a reducer that mutated state and returned the same object:

```text
- {sequence:147,…,type:reports/NOTE_ADDED,…,rootStateChanged:false,changedSlices:[],…,mutation:{status:detected,…,findings:[{path:[reports,notes],change:length-changed}],…}}
```

`redux_state` showed the note in the store, and the page showed zero notes.

## What partial evidence looks like

Partial evidence tells you which component rendered and why it looked unnecessary, but stops at the store. For the avatar menu, Genie showed a store-driven render where nothing changed:

```text
← external-store inferred {reason:external-store-snapshot-changed,…,before:{user:{…},savedViewCount:0},after:{user:{…},savedViewCount:0},changedFields:[],deepDiff:{changes:[{kind:reference-only,path:""}],…},…,selector:null,…,actions:[{…,type:issues/filtersChanged,changedSlices:[issues]}]
```

That is enough to look for a `useSelector` that builds a new object. It is not the line. The board columns and the issue table stop at the same place, because the waste happens inside a reselect selector during the store notification, before any component renders. The leaked poller is a class `setInterval`, which the effect tools do not observe, so the only trace is the 401 traffic after sign-out.

## Where verify has no claim

`verify` decides claims about render counts, render causes, effect runs and error boundaries. Five bugs fall outside that. For each one we repeated the same tool read after the fix:

- In `comment-edit-follows-index`, `isEditing:true` stayed on `c-CORE-12-3`, the comment the user was editing.
- In `search-stale-query`, the request carried `?q=webhook`, and the results read "93 matching issues" instead of 3240.
- In `report-range-race`, the store's throughput range stayed `7d`, and the widget read "9 completed" instead of 33.
- In `lazy-route-blank-shell`, the boundary in `fallback` moved to `app-shell.tsx:30`, and `agent-browser is visible .top-bar` returned `true` during the load.
- In `poller-after-sign-out`, no request to `/api/notifications` followed `DELETE /api/session`.

These reads are evidence, but no exit code decides them. An agent has to compare them itself.

## What Genie got wrong

Know three things before you trust the table.

- After the title fix, the claim `render IssueTitleEditor only props.issue` was refused with exit 4. The one render had an exact `props.issue` cause and an inferred `parent` cause from its `connect()` wrapper, and the refusal fix said only `change-claim`. We switched to `render IssueTitleEditor max 1`, which failed at 2 renders before the fix and passed at 1 after.
- In one of two race runs, `react_inspect_component` on `ThroughputWidget` returned `range:"7d"` in four of five reads, while the DOM's `data-range` and the store both said `90d`. We left that tool out of the race evidence and used the request lane and `redux_actions`.
- On the board, the passing `FeatureGate` claim reported `instances:200` for 840 mounted gates. Before the fix, the same claim counted 840 renders, so the render count is not limited to 200. The `instances` label is still wrong.

## When this approach does not fit

The answer key told us where each bug was. An agent starting cold has to find the screen and the component first, and this run does not measure that. We also did not run the six decoys, the correct code that looks suspicious, so this article makes no claim about false positives. The verdicts come from a development build with StrictMode on. Render counts say nothing about milliseconds. For timing, use the capture comparison in the [optimize guide](/docs/guides/optimize).

[Verify a fix](/docs/guides/verify-a-fix) lists every claim form. The row bug has its own walkthrough in [Select one row and all 100 redraw](/docs/articles/one-click-redraws-100-rows).
